# Kubernetes 监控平台离线部署文档（V2）

## 1. 部署包说明

部署包名称：

```text
monitoring-offline-deploy-v2.0.0.tar.gz
```

校验文件：

```text
monitoring-offline-deploy-v2.0.0.tar.gz.sha256
```

该离线包适用于已经安装好 Kubernetes 的 Linux AMD64 集群，包含：

- kube-prometheus-stack 62.7.0
- Prometheus 2.54.1
- Grafana 11.2.0
- Alertmanager 0.27.0（默认不部署，镜像保留）
- Prometheus Operator 0.76.1
- kube-state-metrics 2.13.0
- node-exporter 1.8.2
- Grafana Kubernetes 控制面板
- Prometheus 数据源
- Prometheus Operator CRD
- 运行所需的全部离线镜像
- Grafana Dashboard、数据源和数据库备份

默认配置：

| 项目 | 配置 |
|---|---|
| Helm Release | `monitoring-offline` |
| Namespace | `monitoring` |
| Grafana NodePort | `31169` |
| Prometheus NodePort | `31212` |
| Grafana PVC | 10 GiB |
| Prometheus PVC | 50 GiB |
| Alertmanager | 不部署（仅资源监控，无需告警） |
| 告警规则（PrometheusRule） | 不创建（仅资源监控） |
| Prometheus数据保留时间 | 10 天 |
| Grafana账号 | `admin` |
| Grafana初始密码 | `prom-operator` |

## 3. 部署前准备

### 3.1 环境要求

目标环境应满足：

1. Kubernetes 集群已经正常运行。
2. 所有 Kubernetes 节点均为 Linux AMD64。
3. 管理节点已经安装 `kubectl` 和 Helm 3。
4. 管理节点的 kubeconfig 可以管理目标集群。
5. 集群已经配置默认动态 StorageClass。
6. 所有可能调度监控 Pod 的节点至少预留 3 GiB 镜像空间。
7. 节点运行时为 containerd、nerdctl 或 Docker。

### 3.2 检查 Kubernetes 节点

```bash
kubectl get nodes -o wide
```

所有节点状态应为：

```text
Ready
```

### 3.3 检查 Helm

```bash
helm version
```

要求为 Helm 3(任意小版本,含 3.0.x)。

> 本包已按三星环境 Helm 3.0.3 兼容性做过调整:
>
> 1. grafana 子 Chart 中依赖 Helm 3.1+ 的 `lookup` 函数已移除;Prometheus 规则模板中的
>    `dig`、node-exporter 中的 `fromYamlArray`(均需 Helm 3.2+)已替换为等价实现。
> 2. 所有命令不再使用 `--create-namespace`(3.2.0+)、`--dependency-update`(3.1.0+)、
>    `--skip-crds`(3.1.0+),统一改为先 `kubectl create namespace` 建命名空间。
> 3. CRD 由 `scripts/02-install-crds.sh` 以 Server-Side Apply 安装;`values.yaml` 中
>    `crds.enabled: false` 已禁用 crds 子 Chart,避免 Helm 以普通方式重复安装 CRD。
> 4. `helm template` 在 Helm 3.0.x 下不可用(默认假定 K8s v1.16.0,且无 `--kube-version`
>    旗标),渲染检查请改用 §8.3 的 `--dry-run` 方式(连集群取真实版本)。

### 3.4 检查默认 StorageClass

```bash
kubectl get storageclass
```

必须至少存在一个带 `(default)` 标记的 StorageClass，例如：

```text
NAME                   PROVISIONER                                   AGE
nfs-client (default)   k8s-sigs.io/nfs-subdir-external-provisioner   20d
```

如果 `nfs-client` 已存在但不是默认 StorageClass，可以设置为默认：

```bash
kubectl patch storageclass nfs-client \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

再次检查：

```bash
kubectl get storageclass
```

### 3.5 检查动态存储供应器

```bash
kubectl get pods -A | grep -Ei 'nfs|provision'
```

对应的动态存储供应器 Pod 应为 `Running`。

## 5. 在所有 Kubernetes 节点导入离线镜像

### 5.1 注意事项

必须在每个可能运行监控 Pod 的 Kubernetes 节点导入镜像。

如果集群有 3 台可调度节点，就必须在 3 台节点上执行镜像导入。否则 Pod 调度到未导入镜像的节点时，会出现：

```text
ImagePullBackOff
```

### 5.2 将部署目录复制到其他节点

如果部署包只在管理节点上，可以复制到其他节点：

```bash
scp -r /data/jiankong/monitoring-offline-deploy-v2 \
  root@目标节点IP:/data/jiankong/
```

### 5.3 在每个节点导入镜像

```bash
cd /data/jiankong/monitoring-offline-deploy-v2
chmod +x scripts/*.sh
sudo ./scripts/01-load-images.sh
```

脚本会依次探测：

- `ctr`
- `nerdctl`
- `docker`

如果使用 containerd，也可以手动导入：

```bash
ctr -n k8s.io images import ./images/monitoring-images.tar
```

### 5.4 检查镜像

```bash
ctr -n k8s.io images list | \
  grep -E 'grafana|prometheus|alertmanager|node-exporter|kube-state-metrics|k8s-sidecar|webhook-certgen'
```

包中主要镜像：

```text
docker.io/grafana/grafana:11.2.0
quay.io/kiwigrid/k8s-sidecar:1.27.4
quay.io/prometheus/alertmanager:v0.27.0
quay.io/prometheus/node-exporter:v1.8.2
quay.io/prometheus-operator/prometheus-config-reloader:v0.76.1
quay.io/prometheus-operator/prometheus-operator:v0.76.1
quay.io/prometheus/prometheus:v2.54.1
registry.k8s.io/kube-state-metrics/kube-state-metrics:v2.13.0
registry.k8s.io/ingress-nginx/kube-webhook-certgen:v20221220-controller-v1.5.1-58-g787ea74b6
```

> 注意：Grafana 的 initChownData init 容器需要 `docker.io/library/busybox:1.36.1`，
> **该镜像不在本镜像包内**，需现场单独导入到所有可调度节点，导入后的镜像名必须与
> `docker.io/library/busybox:1.36.1` 完全一致。

## 6. 安装 Prometheus Operator CRD

在 Kubernetes 管理节点执行：

```bash
cd /data/jiankong/monitoring-offline-deploy-v2
./scripts/02-install-crds.sh
```

也可以手动执行：

```bash
kubectl apply \
  --server-side \
  --force-conflicts \
  -f ./crds
```

必须使用 Server-Side Apply，不能使用普通的：

```text
kubectl apply -f ./crds
```

否则大型 CRD 可能报错：

```text
metadata.annotations: Too long: must have at most 262144 bytes
```

> `scripts/03-install-monitoring.sh` 已内置此步骤（幂等），即使跳过 02，03 也会先以 SSA
> 方式安装/更新 CRD。若目标集群残留**旧版** Prometheus Operator CRD，本步骤会将其覆盖
> 更新——旧版 PrometheusRule CRD 的 duration 正则不认 `10m` 等时长，会报
> `spec.groups.rules.for is invalid`（本包默认不创建告警规则，不会触发该错误；启用告警时必须先跑本步骤）。

检查 CRD：

```bash
kubectl get crd | grep monitoring.coreos.com
```

应包含：

```text
alertmanagerconfigs.monitoring.coreos.com
alertmanagers.monitoring.coreos.com
podmonitors.monitoring.coreos.com
probes.monitoring.coreos.com
prometheusagents.monitoring.coreos.com
prometheuses.monitoring.coreos.com
prometheusrules.monitoring.coreos.com
scrapeconfigs.monitoring.coreos.com
servicemonitors.monitoring.coreos.com
thanosrulers.monitoring.coreos.com
```

## 7. 检查安装配置

查看默认配置：

```bash
cat values.yaml
```

当前持久化配置：

| 组件 | 容量 | 访问模式 |
|---|---:|---|
| Grafana | 10 GiB | ReadWriteOnce |
| Prometheus | 50 GiB | ReadWriteOnce |

> Alertmanager 与告警规则默认不部署（仅资源监控）。如需启用告警：修改
> `chart/values.yaml` 中 `alertmanager.enabled: true` 与 `defaultRules.create: true`
> 后重新安装，并先执行 §6 的 CRD 更新步骤。

`values.yaml` 未固定 `storageClassName`，因此会使用目标集群的默认 StorageClass。

如果需要明确指定 `nfs-client`，可以在 `values.yaml` 对应位置添加：

```yaml
grafana:
  persistence:
    storageClassName: nfs-client

prometheus:
  prometheusSpec:
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: nfs-client
```

## 8. Helm 安装前检查

### 8.1 检查是否有旧 Release

```bash
helm list -n monitoring --all
```

如果存在失败或未完成的 `monitoring-offline` Release，可以清理：

```bash
helm uninstall monitoring-offline -n monitoring || true
```

检查残留 Helm Secret：

```bash
kubectl get secret -n monitoring | \
  grep sh.helm.release.v1.monitoring-offline || true
```

如果确认是失败残留，可以删除：

```bash
kubectl delete secret -n monitoring \
  -l owner=helm,name=monitoring-offline
```

不要删除已经安装的 CRD。

### 8.2 执行 Helm lint

```bash
helm lint ./chart -f ./values.yaml
```

正确结果：

```text
1 chart(s) linted, 0 chart(s) failed
```

### 8.3 渲染检查

```bash
kubectl get namespace monitoring >/dev/null 2>&1 || kubectl create namespace monitoring

helm upgrade --install monitoring-offline \
  ./chart \
  --namespace monitoring \
  --dry-run \
  -f ./values.yaml \
  > /tmp/monitoring-rendered.yaml
```

检查返回码：

```bash
echo $?
```

应为：

```text
0
```

检查 Grafana NodePort：

```bash
grep -n -A3 -B3 'nodePort: 31169' \
  /tmp/monitoring-rendered.yaml
```

检查 Prometheus NodePort：

```bash
grep -n -A3 -B3 'nodePort: 31212' \
  /tmp/monitoring-rendered.yaml
```

检查 Grafana PVC：

```bash
grep -n -A20 -B5 'kind: PersistentVolumeClaim' \
  /tmp/monitoring-rendered.yaml
```

检查 Prometheus 的卷声明模板：

```bash
grep -n -A20 -B5 'volumeClaimTemplate:' \
  /tmp/monitoring-rendered.yaml
```

检查容量：

```bash
grep -n -E 'storage: "?10Gi"?|storage: "?50Gi"?' \
  /tmp/monitoring-rendered.yaml
```

正常应能确认：

- Grafana NodePort：31169
- Prometheus NodePort：31212
- Grafana PVC：10 GiB
- Prometheus volumeClaimTemplate：50 GiB
- 不包含 Alertmanager 资源（默认不部署）

### 9.1 使用部署脚本

```bash
cd /data/jiankong/monitoring-offline-deploy-v2
./scripts/03-install-monitoring.sh
```

### 9.2 完全手动安装

```bash
kubectl get namespace monitoring >/dev/null 2>&1 || kubectl create namespace monitoring

helm upgrade --install monitoring-offline \
  ./chart \
  --namespace monitoring \
  -f ./values.yaml \
  --timeout 15m
```

首次安装建议不添加 `--wait`，让 Helm 先完成资源创建，然后单独观察 Pod 和 PVC 状态。

安装成功时通常显示：

```text
NAME: monitoring-offline
NAMESPACE: monitoring
STATUS: deployed
REVISION: 1
```

> 重要：必须安装 `./chart`，不要执行 `helm install ... .`。

## 11. 检查 PV 和 PVC

```bash
kubectl get pvc -n monitoring
kubectl get pv
```

预计创建：

| 组件 | 预期容量 | 预期状态 |
|---|---:|---|
| Grafana | 10 GiB | Bound |
| Prometheus | 50 GiB | Bound |

Prometheus 的 PVC 由 Prometheus Operator 根据 CR 动态创建，因此可能比 Helm 安装资源稍晚出现。Alertmanager 默认不部署，无对应 PVC。

如果 PVC 为 `Pending`：

```bash
kubectl describe pvc -n monitoring
kubectl get storageclass
kubectl get pods -A | grep -Ei 'nfs|provision'
```

重点检查：

1. 默认 StorageClass 是否存在。
2. NFS provisioner Pod 是否为 `Running`。
3. NFS 服务端是否可访问。
4. NFS 目录权限是否正常。
5. PVC Events 是否报告创建目录或挂载失败。

## 15. 常见问题处理

### 15.1 CRD 报 Annotation 超长

错误：

```text
metadata.annotations: Too long: must have at most 262144 bytes
```

解决：

```bash
kubectl apply \
  --server-side \
  --force-conflicts \
  -f ./crds
```

### 15.2 Helm 进程显示 Killed

错误：

```text
Killed helm upgrade --install ...
```

通常是安装旧版外层 Chart 时，Helm 读取大型镜像归档导致内存不足。

V2 包必须安装：

```text
./chart
```

不要安装：

```text
.
```

检查 OOM：

```bash
free -h
dmesg -T | grep -Ei 'out of memory|killed process|oom' | tail -20
```

### 15.3 Helm Release Secret 超过 1 MiB

错误：

```text
Secret "sh.helm.release.v1.monitoring-offline.v1" is invalid:
data: Too long: must have at most 1048576 bytes
```

原因是安装了旧版外层包装 Chart。

正确命令：

```bash
kubectl get namespace monitoring >/dev/null 2>&1 || kubectl create namespace monitoring

helm upgrade --install monitoring-offline \
  ./chart \
  -n monitoring \
  -f ./values.yaml \
  --timeout 15m
```

### 15.4 Pod 为 ImagePullBackOff

查看 Pod 所在节点：

```bash
kubectl get pods -n monitoring -o wide
```

查看事件：

```bash
kubectl describe pod -n monitoring Pod名称
```

登录 Pod 所在节点重新导入镜像：

```bash
cd /data/jiankong/monitoring-offline-deploy-v2
sudo ./scripts/01-load-images.sh
```

检查镜像是否位于 containerd 的 `k8s.io` namespace：

```bash
ctr -n k8s.io images list | grep 镜像关键字
```

### 15.5 Pod 为 Pending

```bash
kubectl describe pod -n monitoring Pod名称
kubectl get pvc -n monitoring
kubectl describe pvc -n monitoring PVC名称
```

重点检查节点资源、PVC、污点、亲和性和调度事件。

### 15.6 Grafana 页面没有数据

检查 Prometheus：

```bash
kubectl get prometheus -n monitoring
kubectl get servicemonitor -n monitoring
kubectl get pods -n monitoring
```

打开 Prometheus Targets：

```text
http://节点IP:31212/targets
```

确认采集目标状态为 `UP`。

### 15.7 查看 Pod 日志

```bash
kubectl logs -n monitoring Pod名称 --all-containers
```

查看上一次异常退出日志：

```bash
kubectl logs -n monitoring Pod名称 --all-containers --previous
```

### 15.8 安装报 PrometheusRule `for` 校验失败

```text
Error: PrometheusRule.monitoring.coreos.com "..." is invalid:
spec.groups.rules.for: Invalid value: "10m": ...
```

原因：集群残留**旧版** Prometheus Operator CRD（旧 duration 正则不认 `10m` 等时长）。

解决：先执行 `./scripts/02-install-crds.sh`（SSA 方式覆盖更新 CRD），再重新安装。

> 本包默认不创建告警规则（`defaultRules.create: false`），正常情况下不会触发此错误；
> 只有启用告警时才必须保证 CRD 为包内版本。

## 16. 修改存储容量

安装前编辑：

```text
/data/jiankong/monitoring-offline-deploy-v2/values.yaml
```

Grafana：

```yaml
grafana:
  persistence:
    size: 10Gi
```

Prometheus：

```yaml
prometheus:
  prometheusSpec:
    storageSpec:
      volumeClaimTemplate:
        spec:
          resources:
            requests:
              storage: 50Gi
```

Alertmanager 默认不部署。如需启用告警，改 `chart/values.yaml` 中 `alertmanager.enabled: true`
与 `defaultRules.create: true`，并先执行 §6 的 CRD 更新步骤，再重新安装。启用后可参考以下配置调整其存储容量：

```yaml
alertmanager:
  enabled: true
  alertmanagerSpec:
    storage:
      volumeClaimTemplate:
        spec:
          resources:
            requests:
              storage: 10Gi
```

调整后重新执行：

```bash
helm lint ./chart -f ./values.yaml
```

> 已经创建的 PVC 是否支持扩容，取决于 StorageClass 的 `allowVolumeExpansion` 配置。不要直接缩小已有 PVC 容量。

## 18. 卸载

卸载 Helm Release：

```bash
helm uninstall monitoring-offline -n monitoring
```

检查 PVC 和 PV：

```bash
kubectl get pvc -n monitoring
kubectl get pv
```

为防止数据丢失，不要立即删除 PVC、PV 和 Prometheus Operator CRD。

确认数据不再需要后，才可以删除 PVC：

```bash
kubectl delete pvc --all -n monitoring
```

> 删除 PVC 可能永久删除 Prometheus 历史数据、Grafana 配置及 Alertmanager 状态。删除前必须检查 PV 回收策略并完成必要备份。

### Kubernetes 管理节点

```bash
kubectl apply \
  --server-side \
  --force-conflicts \
  -f ./crds

helm lint ./chart -f ./values.yaml

kubectl get namespace monitoring >/dev/null 2>&1 || kubectl create namespace monitoring

helm upgrade --install monitoring-offline \
  ./chart \
  -n monitoring \
  --dry-run \
  -f ./values.yaml \
  > /tmp/monitoring-rendered.yaml

helm upgrade --install monitoring-offline \
  ./chart \
  -n monitoring \
  -f ./values.yaml \
  --timeout 15m

helm list -n monitoring
kubectl get pods -n monitoring -o wide
kubectl get pvc -n monitoring
kubectl get pv
kubectl get svc -n monitoring
```
